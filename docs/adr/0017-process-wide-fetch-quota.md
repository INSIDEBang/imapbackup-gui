# ADR 0017：进程内共享取信字节额度

Status: accepted

取代 ADR 0013 中「不额外加锁，也不做跨账户排队、轮转或启动错峰」「不新增控制器接口、主机注册表、
共享实例」这一条。0013 的其余结论继续有效：无自适应限速、无按服务端速率的退让、固定批量、
不新增设置项、账户之间不共享速率状态。

## Context

每账户一批最多 64 封 / 32 MiB 声明字节（ADR 0015），而账户数量由使用者自己决定：现场只有
2 个账户，界面不设上限，员工机器上可能有更多、邮件量与附件大小也未知。每账户满载时取信内存
约 100–128 MB，7 个账户同时下载就是约 900 MB——**上界随账户数线性增长，与机器无关**。

需要一条不随账户数放大的内存上界。这与 ADR 0013 否掉的东西不是同一件事：0013 否掉的是**按服务端
速率退让**的闭环（共享速率状态、令牌桶、AIMD）；这里共享的是**本机内存预算**，它不观察网络、
不改变批次大小、不构成退让，只让某个账户在取信前多等一会儿。

## Considered Options

- **固定批大小 + 额度不足则等待（采纳）**：批次仍由 ADR 0015/0016 决定，假服务器上的请求次数
  因此是可确定性断言的。
- **批大小随可用额度收缩**：内存利用率最高，但每次运行的请求次数都随调度变化，回归测试与现场
  判定同时失去可比性——这正是 0013 排除的自适应批量。
- **并发下载槽位数（如最多 2 个账户在下载阶段）**：实现最小，但用串行换内存，几秒就能跑完的小账户
  会排在 35 的 40 秒/批后面。
- **不做共享状态、把每账户字节上限收回 16 MiB**：零耦合，但附件型文件夹的收益砍半，且上界仍然
  = 账户数 × 16 MiB。
- **按物理内存自动算额度**：随机器变化的隐藏策略，行为不可预测，也违背「不新增隐式开关」。

## Decision

- 核心新增 `FetchQuota`：进程内的在途正文字节预算，**64 MiB**，按批次的**声明字节**
  （`RFC822.SIZE` 之和）计量。
- GUI 每进程创建一个，随取信调用传入每个账户；CLI 单账户单进程，不传（等价于不受限）。
- 申请点：每个正文批次取信之前；释放点：该批写盘结束之后（异常路径必须释放）。
- 额度不足时**等待**，不缩小批次；等待期间每 0.2 秒轮询协作停止信号，停止能立即打断等待。
- 等待**不烧重连预算、不计入正文取信停滞、不算文件夹失败**，也不新增账户状态。
- 旁路：声明字节 ≥ 整个额度、或大小未知（`RFC822.SIZE <= 0`）的批次**不等待，直接取**——否则
  永远装不进额度会死锁；巨型单封今天本来就是整封读入。
- 扫描阶段不申请额度（头部分页由 500 UID 封顶，不是内存主力）。
- 不新增设置项、不按主机或账户分额度、不做公平调度。

## Consequences

- 并发取信的在途声明字节 ≤ 64 MiB（实际内存约 3–4 倍，~256 MB 级），与账户数无关；超大单封与
  未知大小的批次是明确记录的例外。
- 极端并发下会出现「账户显示备份中、实际在等额度」的窗口。界面上不解释（文案与状态图标不变），
  只在诊断采样留痕：`inflight_msgs` / `inflight_bytes` / `inflight_elapsed_s` / `quota_wait_s`。
  ETA 会把等待算进耗时——这是正确的，它确实更慢。
- 现场两个真实账户几乎不会触发额度（普通批次约 1.5 MiB，小账户几秒完成）：它的正确性只由假服务器
  回归证明，现场只应看到 `quota_wait_s ≈ 0`。因此现场判定吞吐前必须先确认这一点。
- 可单独回退：删掉 GUI 传入额度即可，批次策略不受影响。
