# ADR 0015：正文批次载荷提高到 64 封 / 32 MiB

Status: accepted

Related: [备份吞吐实现规格](../specs/backup-throughput.md) · [README Fork Notes](../../README.md#what-changed-in-160-fork)

取代 ADR 0013 的「每批最多 8 封、8 MiB」常数。0013 的其余结论——无客户端自适应限速、
无跨账户共享速率状态、不新增设置项、CLI 与 GUI 共用同一固定策略——继续有效。
跨账户共享的取信额度另见 ADR 0017。

## Context

两次现场全量运行（账户脱敏为 A，可见批次约 750 个）表明，一次正文取信的耗时与它携带的
邮件数和字节数几乎无关：

- 按每封平均字节分桶：小邮件批次（<100 KB/封）中位 32.1 秒，大邮件批次（≥100 KB/封）中位
  46.7 秒——字节差 40 倍以上，耗时只差 1.4 倍。
- 按封数分桶：2–8 封的批次中位 25–58 秒，看不出随封数增长的斜率；满批（8 封）中位 38.6 秒。
- 同一次运行里，最慢的文件夹 F6 有 816 封、合计仅 4.1 MB，被切成 102 次请求，跑了 557 分钟；
  而 62 MB 的 26 封只跑了 6.8 分钟。本地扫描 313 毫秒，不是瓶颈。

瓶颈是服务端给每个请求的等待。ADR 0013 当时写「35 的实际限速模型未知，不能为不确定的收益
引入跨账户共享状态」；现在数据支持的结论比闭环更简单：**一次请求多装邮件**。

## Considered Options

- **只抬封数、不抬字节（64 封 / 8 MiB）**：小邮件文件夹的请求数降到 1/8，但附件型文件夹仍被
  8 MiB 拆成独占批，等于放掉同一批证据指向的另一半收益。
- **64 封 / 32 MiB（采纳）**：请求数按先到者封顶，小邮件与大邮件两类文件夹都受益。
- **16 封 / 16 MiB**：收益与风险都减半，但两次现场数据没有给出必须保守的理由。
- **自适应闭环 / 加 sleep**：见 ADR 0013；且可见批次耗时占下载段约 87%，客户端并没有空转可省。
- **停下来等「约 50 封的快速窗口」**：突发额度约 48 封 / 约 2 小时空闲 = 0.4 封/分，远低于低速档
  持续跑的 1.2–7 封/分；为它等待是净亏损。
- **调整文件夹顺序**：总请求数不变，只改变哪个文件夹先落盘。

## Decision

- `FETCH_BATCH_MAX_MESSAGES` 8 → **64**；`FETCH_BATCH_MAX_BYTES` 8 MiB → **32 MiB**。
- 切批规则不变：按 UID 升序，封数与声明字节以先到者为准；`RFC822.SIZE <= 0` 或超过字节上限的
  单封独占一批（「超大」的门槛随字节上限一起抬高）。
- 每账户仍是一个连接、同一时刻至多一个请求在途；批间不休眠、不拿令牌、不做 AIMD。
- 不新增 CLI 参数、不新增 GUI 设置项、不预留开关；扫描的 500 UID 分页不在本决策范围内。

## Consequences

- 小邮件文件夹的请求数最多降到 1/8；混合待备份集预期降到约 1/4。收益能否兑现取决于服务端是否
  真的按请求而非按字节惩罚——这只有现场冷跑能证伪。
- 每账户取信期间的内存峰值按声明字节的 3–4 倍估算（ imaplib 响应、原始字节、mbox/eml 各一份
  副本），满载最坏约 100–128 MB。并发总量由 ADR 0017 封顶；超大单封不受封顶，与今天一致。
- 进度、计数与邮件列表改成**成块推进**：一次最多 64 封在同一瞬间到账，之后可能有约 40 秒静默。
  这是有意的，不是卡住；README 的 Fork Notes 需要一句话说明。
- 回退方式：把两个常数改回 8 / 8 MiB 的一次独立提交，不留开关；现场判定线见规格与本次验收约定。
