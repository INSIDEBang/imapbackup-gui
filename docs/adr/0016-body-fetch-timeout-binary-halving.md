# ADR 0016：正文取信超时按对半缩小批次重取

Status: accepted

取代 ADR 0014 的「超时后逐封拆单封重取」粒度。0014 的其余结论继续有效：只有 `TimeoutError`
进入这条路径、`BatchStalled` 仍重建链路但不占重连预算、**只有单独取仍超时才计入 `timeout`
并本轮放弃**、不跟踪停滞的旧调用方保持原行为。

## Context

ADR 0014 是在「每批最多 8 封」的前提下设计的，最坏情况是一次超时放大成 8 次单封往返。批次
上限提高到 64 封 / 32 MiB（ADR 0015）之后，同一逻辑变成一次超时放大成 64 次往返，每次还要
各自付一次读超时（现场为 61–63 秒）与一次重建链路。

而超时的成因往往是**请求本身太大**（服务端读得慢或直接不给响应），不是某封邮件读不动：现场
两例分别是一批 8 封 / 3.6 MB 与一批 8 封 / 29 KB 超时，随后单独重取仍然超时。逐封拆在两种
情况下都会把代价乘以批大小。

## Considered Options

- **对半缩小（采纳）**：批内各封的批次上限逐次减半；若服务端只是读不动大批次，2 次请求就能救回
  整批。
- **保持逐封拆**：实现不动，但 64 封规模下的尾部代价变成今天的 8 倍。
- **设 8 封地板、永不逐封**：坏邮件无法定位，一放弃就是一整批 8 封，违背 ADR 0014 的放弃契约。
- **每文件夹停滞次数封顶（如 32 次后记文件夹失败）**：上限表每轮运行清空，下一轮会重演同一场
  灾难，把「部分完成」变成「每次必输」。

## Decision

- `BatchStall` 的状态从「下一轮必须独占一批的 Message-Id 集合」改为**每封的批次大小上限表**
  （Message-Id → 上限）。
- 一个批次超时：批内各封的上限对半（64 → 32 → 16 → 8 → 4 → 2 → 1，向上取整），**只降不升**；
  本文件夹本轮内保持，下一轮运行新建即重置。对半的对象是**这一批实际带的封数**——受字节上限
  约束而不足 64 封的批同样缩得下来，否则下一轮会原样重发同一个请求。
- 切批尊重上限：一批的封数硬上限是批内成员上限的最小值；上限为 1 的成员独占一批——即 0014 的
  旧行为是新表的特例。
- 放弃条件不变：某封上限已到 1，且**单独取仍然超时**，才计入 `fetch_failed(timeout)`、本轮该
  文件夹不再请求它；下一轮运行自然重新成为待备份。
- `BatchStalled` 仍视为可重试的连接级错误（重建链路），仍不增加连续失败预算、不叠加抖动退避。

## Consequences

- 最坏代价上升但有界：64 封全部需要隔离时，共 126 次请求、每次附带一次 60 秒读超时与一次重建
  （约 2 小时）；同规模在 8 封/批下最坏约 1.2 小时，即约 1.75 倍。外部刹车只有现场中止线。
- 上限单调 → 一个文件夹一旦退化到单封，本轮不会再合并回大批次；这是刻意的，避免在同一批上反复
  付超时。
- 超时仍是罕见路径：两次现场运行各只有 2 次超时。
- 失败计数、诊断字段与账户收口口径（部分完成）不因本决策改变。
