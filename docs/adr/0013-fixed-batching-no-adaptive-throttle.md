# ADR 0013：固定批量、无客户端自适应限速

Status: accepted

取代备份吞吐 effort 中「自适应闭环 + 同主机共享总速率」的早期结论，
并确认固定批量、无共享控制器的最终选择。

## Context

35 云邮在备份到约 50 封后会静默降速。服务商没有公开限速条款，客户端无法从协议层
判断限速按消息数、字节数还是时间窗计，也无法区分服务端限速、网络拥塞与本地磁盘慢。

早期设计倾向于一个跨账户共享的自适应控制器：按主机聚合速率，用 AIMD/令牌桶在
「变慢」时退让，在「恢复」时加速。一次离散事件仿真对比了固定延迟、AIMD 批量、
令牌桶 + AIMD、p95 延迟降档与固定批量：

- 常规网络模型下，固定 8 封批量已经匹配或超过所有闭环方案；闭环的探测与退让在
  服务端没有惩罚型限速时只会增加空转。
- 只有在「服务端按近期请求量惩罚后续请求」的模型里，闭环才有保险价值；而 35 的
  实际模型未知，不能为不确定的收益引入跨账户共享状态。
- 6–7 个账户 × 每账户 8 封 = 约 48 封在途，请求仍然短；再叠加客户端 sleep/队列只会
  拉长首量时间。

后续架构决策进一步确认：不新增控制器对象、主机注册表、共享实例或空壳参数；CLI 与 GUI
共用同一固定批量策略；账户之间不存在任何共享限速状态。

## Considered Options

- **自适应闭环 + 每主机共享速率（早期方案）**：在惩罚型限速下可能更稳，但状态、公平性、
  设置与测试成本高；常规模型下更慢，且与 ADR 0012 的账户独立运行模型冲突。
- **固定批量 8 封 / 8 MiB，每账户单请求在途（采纳）**：实现最小，行为可预测，CLI/GUI
  完全一致；把「是否需要客户端退让」交给现场诊断决定。
- **固定批量 + 可选并发/速率设置**：给用户调参，但 v1 明确不新增设置，且非技术用户
  难以判断；暂不采纳。
- **完全逐封（维持现状）**：往返次数最多，首量最慢，不满足吞吐目标。

## Decision

### v1 策略

- 正文固定批量：每批最多 8 封、8 MiB（按 `RFC822.SIZE` 求和）；单封超过 8 MiB 独占一批；
  批间不休眠、无令牌桶、无 AIMD。
- 扫描固定分页：`UID SEARCH ALL` 后每 500 UID 一次头部 `UID FETCH`；扫描不套正文批量。
- 每账户一个连接；`imaplib` 同步模型保证同一时刻至多一个请求在途；不额外加锁，也不做
  跨账户排队、轮转或启动错峰。
- 不新增控制器接口、主机注册表、共享实例、CLI 参数或 GUI 设置；不预留空壳。
- 账户之间只共享本地扫描索引（判重缓存）与日志目录，不共享限速状态。
- 断线重连是调用方的有界重试，不是调速器：只处理连接级错误，最多 5 次连续失败，
  指数退避 + 全抖动（约 2 秒到 5 分钟），成功后预算清零。

### 重评触发条件

出现任一情况时，另开决策工单，不在本版本内临时加 sleep 或隐藏开关：

1. 现场 `diag-*.jsonl` 显示持续锯齿：速率周期性冲高后长时间塌陷，且不是网络/本地磁盘
   造成。
2. 取信失败/NO/BYE 比率随并发账户数明显上升。
3. 服务商公布明确的请求数/字节数/时间窗限额。
4. 验收显示固定批量在真实大账户上持续低于旧版基线的 80%，且有服务端降速证据。
5. `COMPRESS=DEFLATE` 等服务端能力被证实可用且收益明确（另一个决策）。

### 未来引入控制器的前提

若重评后决定引入自适应控制，必须是**新 ADR**，并同时决定：

- 控制器归属（核心/GUI）与跨账户共享键（主机/端口/SSL/账户）。
- 是否新增设置项、默认值与用户可见文案。
- 与 ADR 0012 独立停止/追加/冷却的交互。
- 与本地索引、诊断采样的字段扩展。

v1 不为这些未来选项预留接口；避免「空控制器」变成事实上的架构。

## Consequences

- 实现与测试显著简化：核心只有切批、失败矩阵、重连三块；没有跨账户共享状态，
  停止、追加、失败、冷却都不需要重置控制器。
- 客户端不承诺解决服务端限速：若 35 在几十封后持续降速，v1 只能保证「不失控、可恢复、
  有数据」，并在验收中标记「未解决」。这是有意的取舍，不是遗漏。
- 首量吞吐依赖服务端调度；某账户分到的份额偏少时，只能靠现场诊断发现，客户端不做
  公平调度。
- 固定批量对超大单封不友好：单封超 8 MiB 仍整封读取，内存峰值随附件大小上升；
  v1 不引入 `imaplib.partial()` 流式后备（Python 3.12.13 不可用）。
- 诊断采样成为后续决策的唯一证据来源；若诊断关闭/写失败，重评条件无法判断，因此
  诊断写失败只降级、不影响备份，但会在运行日志留下 WARNING。
- CLI 与 GUI 行为一致，不出现「GUI 限速、CLI 不限速」的分裂；CLI 不写诊断，现场数据
  需要 GUI 运行。
